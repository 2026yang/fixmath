# FixMath · 采集助手（P0）

任意程序里用左键选中公式 → 按 `Ctrl+Alt+7` → 自动按选区截图、去掉选中高亮、归一化成黑字白底、弹预览并保存到磁盘。

**不依赖 UI Automation，不挑应用**：逻辑是“从屏幕像素里把应用自己画的选区高亮找回来”，所以 Word / WPS / 浏览器 / PDF / 图片查看器都走同一条路径。

## 运行

双击 `run_capture.bat`（或在本目录执行 `python -m fixmath.app`）。

> 必须用普通权限启动，且**不要**从受限的自动化/沙箱会话里启动——低完整性级别进程收不到普通程序的键鼠事件（本机自测就撞到了这一点）。

启动后：

1. 在任意程序里按住左键拖选公式（或双击选词）；
2. 按 `Ctrl+Alt+7`；
3. 光标旁弹出裁剪预览，同时写入
   `%LOCALAPPDATA%\FixMath\captures\<时间戳>\`。

按 `Ctrl+C`（控制台窗口）退出。

### 为什么不是 Ctrl+Alt+M

WPS 把 `Ctrl+Alt+M` 当成本地快捷键（会进入编辑模式）。助手现在用**键盘低级钩子**接管组合键：命中时 `return 1` 把按键吞掉，前台程序根本收不到，所以不会再触发 WPS 的编辑模式。

但为了彻底避开冲突，默认组合改成了 `Ctrl+Alt+7`（数字键好按，也不容易和编辑器快捷键撞车）。想换键就建一个

`%LOCALAPPDATA%\FixMath\config.json`

```json
{ "hotkey": "ctrl+shift+alt+m" }
```

支持 `ctrl / alt / shift / win` + 字母、数字或 `f1`–`f24`，例如 `ctrl+alt+f9`。改完重启助手生效。

### 按了没反应时

助手现在会写日志：`%LOCALAPPDATA%\FixMath\helper.log`。按顺序看：

1. 控制台有没有 `已启动，热键 CTRL+ALT+7`？没有就是没跑起来。
2. 日志里有没有 `[hook] 已安装 mouse=True keyboard=True`？没有就是钩子没装上。
3. `进程完整性级别: low` 说明是从受限环境（沙箱/某些终端）启动的，普通程序不会把键鼠事件发给你，必须普通双击启动。
4. `[key] 按到了 vk=0x37，但修饰键是 ...` 说明键收到了、但组合不对（常见于键盘布局需要 Shift 才能打出 7）。
5. `已经有一个助手在运行` 说明旧实例还在，先关掉它（任务管理器结束 `python.exe`）。
6. 数字键同时支持主键盘 `7` 和小键盘 `7`。

## 输出

| 文件 | 内容 |
|---|---|
| `crop.png` | 原始裁剪（保留选中高亮） |
| `clean.png` | 去高亮、黑字白底、必要时放大到 ≥96px 高（**这张是给 OCR 的**） |
| `shot.png` | 截取时的上下文区域 |
| `debug.png` | 画出了拖拽框（黄）、高亮框（青）、最终框（绿），用来排查选区 |
| `meta.json` | 全局坐标、尺寸、模式、耗时 |

`%LOCALAPPDATA%\FixMath\captures\latest.json` 和 `latest.png` 指向最近一次结果，编辑器后续直接读这两个文件即可。

## 选区是怎么算出来的

```
鼠标拖拽（全局低级钩子）── 只作为“种子”，不是最终框
        │
屏幕像素 ──> 背景色估计 ──> 选区高亮检测（颜色 + 形状 + 连通域）
        │                        │
        │                        ├─ 命中：高亮包围盒就是选区真值
        │                        └─ 未命中：拖拽框 + 文本行/墨迹扩展
        ▼
墨迹包围盒收窄（去掉行尾空白、段落标记）──> 四周 pad 6px
```

- 高亮是真值：应用已经把“选中了哪些字”画在屏幕上了。
- 墨迹收窄：Word 选中整行时高亮会连行尾空白一起画，直接截会把大片空白喂给 OCR。
- 深浅主题、白字蓝底、黑字蓝底都用同一个仿射映射归一化成黑字白底。

## 自动化测试

```bash
python tests/selftest.py      # 6 组合成场景（高亮/无高亮/单击/深色/高亮超长/精确拖拽）
python tests/e2e_capture.py   # 真实屏幕抓取 + 真实窗口 + 150% DPI 缩放
python tests/e2e_hotkey.py    # 完整链路：独立助手进程 + 钩子 + 热键 + 真实 Text 选区
python tests/swallow_test.py  # 组合键是否被吞掉、不再传给前台程序
```

本机结果：

- `selftest`：6/6 通过，裁剪框与墨迹真值 IoU 0.998–1.000，单次 36–84 ms（不含截屏）；
- `e2e_capture`：3/3 通过，含“零高度拖拽”（纯水平拖选）场景，150% 缩放下坐标不错位；
- `e2e_hotkey`：通过。钩子记录拖拽 `(288,354)-(1259,354)`，热键后 80 ms 按高亮裁出 `1060×123`，白字蓝底正确归一化；
- `swallow_test`：通过。间谍钩子只看到 Ctrl/Alt，**没有看到 Q**；普通 Q 仍能正常到达。

`tests/input_test.py`（真实注入鼠标/热键）必须在普通权限下运行；低完整性级别会话里钩子收不到事件，会失败。

## 已知边界

- 目标程序以**管理员身份**运行时，普通权限的助手收不到它的输入、也钩不到它的窗口；需要同样提权运行（会有 UAC）。
- 完全不画选区高亮、也不暴露光标的程序，会退化为“点击点所在行 + 墨迹扩展”，需要手动拖一下更准。
- 用键盘 `Shift+方向键` 选的公式没有拖拽矩形，只能靠点击点或高亮兜底。
- 独占全屏游戏、DRM 保护画面截不到（系统限制）。
- 目前一次只处理一个矩形；跨多行公式会得到一个整体的框，OCR 阶段再按行切。
